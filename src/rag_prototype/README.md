# RAG 프로토타입

PDF를 올리면 문서 내용을 근거로 답하는 RAG 챗봇. 1단계 MVP의 "사내 문서 RAG" 뼈대다.

## 구조

| 파일 | 역할 |
|---|---|
| `rag_module.py` | RAG 파이프라인 8단계 (로드 → 분할 → 임베딩 → FAISS → 검색 → 프롬프트 → Claude → 출력) |
| `app.py` | Streamlit 화면 (PDF 업로드, 채팅) |
| `prompts.py` | 프롬프트 버전 모음 (v0 원래 예제 → v3.1 기본값 → v4 단계적 사고). `.env`의 `PROMPT_VERSION`으로 선택 |
| `check_retrieval.py` | 검색 진단: 질문별 상위 조각과 정답 조각의 순위 출력, `--rerank`로 리랭킹 전후 비교 (LLM 호출 없음) |
| `requirements.txt` | 이 폴더 전용 패키지 목록 |

LangChain 기본 RAG 예제 구조에서 시작해 아래를 바꿨다.

- 답변 모델: Claude (`langchain-anthropic`). 모델명은 `.env`의 `ANSWER_MODEL`
- 임베딩: Claude는 임베딩 모델이 없어 로컬 모델 `BAAI/bge-m3` 사용 (API 비용 없음). 처음에 쓴 `ko-sroberta-multitask`보다 검색 순위가 크게 좋아짐 (아래 실험 기록)
- `chunk_size`, `chunk_overlap`, `k`, `search_type`, 프롬프트 버전을 `.env`로 분리해 코드 수정 없이 실험
- 리랭커(`BAAI/bge-reranker-v2-m3`)를 `.env`의 `RERANK`로 켜고 끌 수 있게 함
- 검색된 조각을 "[N쪽] 내용" 형식으로 넘겨 LLM이 출처 쪽수를 쓸 수 있게 함
- 다른 PDF를 올리면 체인을 새로 만들도록 수정, 업로드 파일은 OS 임시 폴더에 저장
- 쪽을 이어 붙인 뒤 분할(`SPLIT_MODE=merged`): 쪽 번호 꼬리말을 지우고 이어 붙여, 쪽을 넘어가는 목록이 한 조각에 들어가게 함. 조각 쪽수는 "4~5쪽"처럼 범위로 표기
- 답변 아래 "근거 조각 보기"로 Claude가 받은 조각과 쪽수를 확인

## 실행

```bash
pip install -r src/rag_prototype/requirements.txt
cp .env.example .env          # ANTHROPIC_API_KEY 입력
cd src/rag_prototype
streamlit run app.py
```

첫 실행 때 임베딩 모델(약 2GB)을 내려받느라 몇 분 걸린다.

## 실험 기록

질문 "이 사업의 배경과 목적이 뭐야?"에 대해 정답 조각(RFP 2쪽 "사업 배경 및 목적")이 몇 등으로 검색되는지 `check_retrieval.py`로 측정했다.

| 설정 | 정답 조각 순위 | 상위 % | 결론 |
|---|---|---|---|
| chunk 400 / overlap 100 / ko-sroberta | 14 / 75 | 19% | 기준. k=3, 6 모두 "문서에 없다"고 답함 |
| chunk 200 / overlap 50 / ko-sroberta | 26 / 145 | 18% | 청크 크기는 원인이 아님 |
| chunk 400 / overlap 100 / bge-m3 | 1 / 75 | 1% | 임베딩 모델이 핵심 원인 |

bge-m3로 바꾼 뒤 앱에서 같은 질문을 다시 했을 때:

| 질문 | ko-sroberta | bge-m3 |
|---|---|---|
| 이 사업으로 기업이 얻고 싶은 것 3줄 | X "문서에 없다" | O 사업 목적 3줄 요약 |
| 이 사업의 기대효과 | X 제안서 작성 지침으로 답함 | O "기대효과 항목은 없다"고 밝히고 사업 목적을 근거로 답함 (7개 중 5개) |

남은 문제: 목적 항목이 2~3쪽에 걸쳐 있어 3쪽 항목 2개가 빠짐. PDF를 쪽 단위로 읽어 분할하기 때문 → 쪽을 이어 붙인 뒤 분할하는 방식 검토.

관찰: 기존 모델에서는 "사업", "목적"이 반복되는 제안서 작성·입찰 절차 조각(목차 표, 평가 기준, 일정)이 상위 10개를 모두 차지했다.

### 프롬프트 버전 비교 (bge-m3, chunk 400/100 고정)

질문 6개(배경·목적, 기대효과, 보안 요구사항 전체, 제출 기한, 문서에 없는 질문, 평가 배점)를 RFP 원문과 대조해 채점했다.

| 버전 | 정확도 | 출처 | 형식 | 군더더기 | 투명성 | 길이 |
|---|---|---|---|---|---|---|
| v0 원래 예제 | 4/6 | 없음 | 제각각 | 있음 | 낮음 | 짧음 |
| v2 역할 + 제약조건 | 4/6 | 있음 (8곳 모두 정확) | 제각각 | 있음 | 보통 | 짧음 |
| v3 + 형식 지정 | 4/6 | 항목별 | 통일 | 질문마다 다름 | 보통 | 보통 |
| v4 + 단계적 사고 | 4/6 | 일부 생략 | 통일 | 질문마다 다름 | 높음 | 김 |

관찰:
- 프롬프트는 정확도가 아니라 신뢰성(출처)·사용성(형식)·투명성을 바꿨다.
- v2의 "문서에 없으면 정해진 문구로 답하기", "유지보수 내용과 보안 요구사항 구분" 규칙은 실제로 지켜졌다.
- v3의 "세부 내용" 칸이 오히려 군더더기를 늘렸다. 제출 기한 질문에 묻지 않은 담당자 이름·이메일·전화번호까지 출력 → 사내 문서였다면 개인정보 노출. "질문과 직접 관련된 것만", "묻지 않은 개인 연락처 출력 금지" 조건 필요.
- v4의 판단 과정은 디버깅에 유용하지만, 검색되지 않은 조각은 알 수 없어 "모두 답할 수 있다"고 틀린 확신을 보였다.
- 누락 2건은 모든 버전에서 그대로 → 원인은 프롬프트가 아니라 검색·추출 단계:
  - 배경·목적 7개 중 2개 누락: 항목이 2~3쪽에 걸쳐 쪽 단위 분할에서 잘림
  - 평가 배점 30점·20점 누락: 다단 표가 텍스트로 추출되며 항목 이름과 숫자가 떨어짐

결정: 서비스 기본값은 v3, 원인 분석용으로 v4.

### 검색 방식 비교: similarity vs mmr (v3 프롬프트 고정)

| 질문 | similarity | mmr |
|---|---|---|
| 배경·목적 | △ 5/7 | △ 5/7 |
| 기대효과 | O | X "문서에서 찾을 수 없습니다" |
| 보안 요구사항 전체 | O 8개 | X 3개만 찾고 "세 가지입니다"라고 단정, 관련 없는 비밀유지 조항 포함 |
| 제출 기한 | O | O |
| 문서에 없는 질문 | O | O |
| 평가 배점 | △ | △ (15점·20점 항목까지 누락) |
| 정확도 | 4/6 | 2/6 |

관찰: mmr은 첫 조각과 비슷한 조각을 중복으로 보고 버린다. 보안 요구사항처럼 한 목록이 이어진 조각 여러 개에 나뉜 경우, 나머지 조각이 버려지고 다른 주제 조각이 섞인다. 검색이 부실하면 모델은 받은 조각만 보고 "세 가지입니다"처럼 틀린 답을 단정한다.

결정: 검색 방식은 similarity 유지.

### 리랭커 (bge-reranker-v2-m3, 후보 20개 → k=3)

`check_retrieval.py --rerank`로 누락 원인 조각의 순위를 리랭킹 전후로 비교했다.

| 질문 | 확인한 조각 | 임베딩 순위 | 리랭킹 순위 | 효과 |
|---|---|---|---|---|
| 보안 요구사항 전체 | 8쪽 TLS 포함 조각 | 3 / 75 | 5 / 20 | 역효과 (k=3에서 탈락) |
| 평가 배점 | 14쪽 "수행체계의 적정성" | 26 / 75 | 후보 밖 | 적용 불가 |
| 배경·목적 | 5쪽 "AI 관련 법제도" | 11 / 75 | 8 / 20 | 소폭 개선, k=3 밖 |

관찰:
- 리랭커는 질문 단어("보안")가 직접 나오는 조각을 올렸다. 제안서 목차의 "품질, 보안… 요구사항", "보안에 적합한 모델 선정"(20등 → 4등)이 올라가고, 구체 항목만 나열된 실제 보안 요구사항 조각은 내려갔다.
- 리랭킹 점수가 모두 낮았다(최고 0.225). 목록 일부만 담긴 조각은 어느 것도 완전한 답이 아니어서다.
- 리랭커는 1차 후보 안의 조각만 다시 정렬하므로, 임베딩 순위가 낮은 조각은 구제하지 못한다.

결정: 이 문서에서는 리랭커를 끈다(`RERANK=false`). 남은 누락의 원인은 검색 순위가 아니라 분할 단계(쪽 단위 분할, 표 추출)다.

### 개선 1: 쪽을 이어 붙인 뒤 분할

| 분할 방식 | 조각 수 | 배경·목적 7개가 한 조각에 | 쪽 꼬리말 남은 조각 |
|---|---|---|---|
| page (쪽마다 분할) | 75 | X (4쪽·5쪽 조각으로 갈림) | 28 |
| merged (이어 붙인 뒤 분할) | 69 | O ("4~5쪽" 조각 하나) | 0 |

### 개선 2: v3.1 프롬프트

v3에서 "세부 내용" 칸을 채우려고 묻지 않은 담당자 이름·이메일·전화번호를 출력한 부작용을 막기 위해 두 조건을 추가했다.
- 질문에 직접 답하는 내용만 쓰고, 묻지 않은 정보는 덧붙이지 않는다.
- 개인 연락처는 질문이 직접 요구할 때만 쓴다. 세부 내용은 필요 없으면 생략한다.

### 개선 1·2 적용 후 답변 (v3.1, merged, k=3)

| 질문 | v3 + page | v3.1 + merged |
|---|---|---|
| 배경·목적 | △ 5/7 | O 7/7 (근거 4~5쪽) |
| 기대효과 | O | O |
| 보안 요구사항 전체 | O 8/8 | △ 7/8, 인프라 요구사항(MSP 운영)을 보안요구사항으로 잘못 포함 |
| 제출 기한 | O + 담당자 연락처 | O, 연락처 사라짐 |
| 문서에 없는 질문 | O | O |
| 평가 배점 | △ 15·15 | △ 15·20 (30점 여전히 누락) |

관찰:
- v3.1의 "묻지 않은 정보·연락처 금지"는 의도대로 동작했다.
- 분할 방식을 바꾸자 조각 경계가 전부 새로 그어져, 보안 목록이 조각 3개(18·19·20번)로 갈렸다. k=3에서 마지막 조각("국내 서버 한정")이 빠지고, "보안" 단어가 든 인프라 조각이 대신 들어왔다.
- 고정 길이 분할에서는 한 경계를 고치면 다른 경계가 새로 생긴다 → 제목 기준 분할 필요.
- 근거 쪽수: 코드는 "11~12쪽"으로 붙였지만 모델이 답변에 "11쪽"으로 줄여 썼다.
